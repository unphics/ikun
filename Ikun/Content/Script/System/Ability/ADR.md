# 战斗系统
- 模块范围: 属性, 技能, 效果, 增益, 标记, 事件, 目标
- 核心需求:
    - 属性派生与依赖计算
    - 临时数值与结算管线
    - 周期性效果与生命周期控制
    - 效果叠加/刷新与转化规则
    - 标签交互/状态互斥/条件限制
    - 属性实时取值与快照语义
- 普适需求示例:
    - 每1点力量增加5点生命上限和2点攻击力
    - 伤害进入结算管线后依次处理护盾、减伤、无敌与扣血
    - 持续10秒每秒扣血
    - 毒可以叠加5层, 每层独立计时
    - 点燃再次施加时刷新时间但不增加层数
    - 处于眩晕状态时无法使用位移技能
- 复杂需求验证用例:
    - 让目标进入中毒状态持续(10+来源者等级*0.1)秒, 每层独立计时, 多个来源可叠加, 每多一层, 第当前层的伤害乘以0.9^层数, 每0.5秒造成一次伤害, 伤害值是来源的最大血量值的1%
- 非目标:
    - 不负责AI决策, 仅提供技能与效果执行能力
    - 不直接处理输入绑定, 输入层只触发技能或能力
- 关键设计约束:
    - 规则应尽量数据驱动, 避免为单个技能编写专用逻辑
    - 效果执行流程要可追踪, 便于调试结算结果
## 技能模块
- 定位: 管理与执行技能相关的所有行为
- 意义:
- 概念:
    Ability(能力):
        - 简介: 一项能力的综合; 可以持有一些技能(如火球术能力持有发射火球和火球爆炸技能); 负责处理冷却和消耗等; 持久存在
    Skill(技能): 一些行为序列的集合; 每次技能触发时实例化技能
## Buff模块
- 定位: 挂载在目标身上的状态容器, 用于承载一个或多个效果器及其生命周期
- 职责: 生命周期管理, 视觉上表示"同一类概念效果"
- 配置: BuffId, BuffName, BuffDesc, SourceMatchRule,
- Buff与Effect功能划分草案:
    - Buff里是有很多Effect的, 也就是Effect数组或者Id数组
    - 首先肯定可以确定的是, Effect肯定是用于处理某一个属性, 那么自然就要获取层数, 自然需要和层数相关的所有信息
    - 如果持续时间和层数绑定, 那么持续时间和层数就是强耦合
    - 动态持续时间下, 同一个Buff下的所有效果的持续时间是同一份
    - 所以设计成Buff中有主导时间的Effect和不主导时间的Effect(即跟随Effect)
    - 合并规则组成草案:
        - 来源判断方式: 按施法者, 按技能, 全为同源, 全为异源, 自定义
        - 同源合并规则: 独立存在, 刷新持续时间, 增加层数并刷新持续时间, 替换已存在, 不替换已存在, 保留强者, 自定义
        - 异源合并规则: 独立存在, 刷新持续时间, 增加层数并刷新持续时间, 替换已存在, 不替换已存在, 保留强者, 自定义
        - 层数上限归属: 每实例, 每来源, 全局共享, 自定义
        - 层数计时规则: 所有层共享时间, 每层独立计时, 自定义
        - 层数溢出处理: 拒绝新层, 替换最旧层, 替换最弱层, 触发额外效果, 自定义
        - 属性读取规则: 施加时快照, 实时读取, 每层独立快照
    - 区分建议:
        - Buff: 生命周期协调
        - Effector: 主动执行
        - State: 纯数据
    - 看"是否存在多个变化维度"
        - 当一个系统同时存在:
            1. 多种计时
            2. 多种Stack
            3. 多种触发条件
            4. 多种生命周期规则
            5. 多种属性修改类型
        - 就说明需要拆层, 而不是塞进一个类
## 效果模块
- 定位: 一段时间内周期性地影响和修改单位的属性与状态
- 意义: 实现一个数据驱动/可扩展/基础功能充足的效果器模块
- 职责: 触发与执行效果, 管理效果的组合与优先级, 数据驱动, 管理周期性与持续时间
- 配置: EffectId, 
- 与其他模块关系:
    - 与技能: 技能对目标施加效果器
    - 与属性: 效果器影响目标属性
## 属性模块
- 定位: 描述单位在当前时刻的数值状态
- 意义: 提供一个稳定/可扩展/可依赖分析的数值状态系统
- 职责:
    - 存储基础属性, 计算派生属性, 管理属性之间的依赖关系, 接收并应用属性修改, 对外提供当前最终属性值
- 构成:
    - AttrSet(属性集): 属性集合; 持久存在, 提供最终属性读取, 内部动态更新, 添加与移除属性修改器
    - AttrManager(属性管理器): 管理属性的定义规则与依赖结构, 属性的规则层; 加载属性配置, 解析属性公式, 建立属性依赖关系, 生成属性集实例
    - AttrModifier(属性修改器): 对某一属性施加影响的一个数值变更单元, 一条对属性的修改规则
- 属性修改器聚合规则:
    1. 按类别聚合(常见于RPG, ARPG, MMO)
        - 把同类Modifier聚合后统一计算, 而不是施加顺序逐个执行
        - 例如: 最大血量100 -> BuffA(+5%MaxHp) -> BuffB(*5%) -> BuffC(+5%MaxHp)
        - 通常先把所有加法归一, 再处理乘法, 或者采用分阶段计算
        - 优点: 结果稳定, 可预测; 易于存档/同步/调试; 策划更容易理解最终数值
    2. 按施加顺序聚合(常见于卡牌, Roguelike, 组合链)
        - 例如: +5% -> *5 -> +5%
        - 最终结果依赖顺序, 适合强调"效果链""触发链"的玩法
        - 优点: 组合空间大, 顺序本身可成为玩法
        - 缺点: 不可预测, 难debug, 数值更难平衡
- 与其他模块的关系:
    - 与技能: 技能读取属性, 技能不修改属性结构, 技能通过Modifier影响属性
    - 与效果器: 增益持有Modifier, 增益将Modifier添加到属性集, AttrSet负责数值更新
## 组件模块
- 概念:
    Part(相当于组件): 一个单位的战斗能力的体现, 包含能力数组/Buff容器/属性集等数据和对应功能

# 游戏工程阶段性演变
- 一个游戏工程里, 会不会因为需求复杂度增长而出现"新架构推翻原架构3层以上"的情况? 会, 而且很常见, Buff系统是非常容易随需求演化的部分, 场景的演化路径:
    1. 极简层:
    ```
    class PoisonBuff {
        Duration;
        OnApply();
        OnTick();
        OnRemove();
    };
    ```
    2. Buff + Modifier: 开始把"属性修改"抽出来
    3. Buff + Effector + Modifier: 开始支持伤害/治疗/事件等更复杂行为
    4. 加入BuffState: 开始把快照/计数/内部变量独立出来
    5. 加入EffectRuntime/ScheduleMetadata: 开始支持不同效果不同计时
- 这是推翻吗?
    - 多数情况下, 这不是推翻, 而是: 抽象层次变细, 职责拆分更明确, 旧层被重新解释或下沉
    - 真正的大推翻通常发生在: 早期抽象方向错了, 一开始把所有东西都塞进一个Buff子类里, 后来发现完全不适合扩展
- 结论: 会大幅重构, 但更理想得是: 通过逐步加层/拆职责来演化, 而不是一次性推倒重来
