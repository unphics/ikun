## 编程的时候感觉逻辑很混乱, 如何才能理清逻辑关系?
- 本文参考自: 编程的时候感觉逻辑很混乱，如何才能理清逻辑关系？ - 人月聊IT的回答 - 知乎 https://www.zhihu.com/question/1964975284659939164/answer/1991246677261185313
### 1. 认知的基石: 理解编程思维的本质映射
- 编程的实际难点不在算法本身或数据结构本身, 而是拿到问题的时候知道如何解决和分析问题, 并将其映射到最合适的算法或数据结构上, 这个映射其实本身不是程序解决的问题, 还是人脑在思维, 程序本身仅仅是在实现自动化的过程
- 逻辑混乱往往是因为开发者跳过了这个映射的阶段
    - 1. 业务: 现实世界的问题, 充满个性化的具体的描述 (用户下订单时, 如果没有库存那么要提示, 如果有优惠券也要提示)
    - 2. 思维: 大脑中的加工过程, 把具体的业务抽象成模型 (库存是一个状态, 优惠券是一个策略类)
    - 3. 代码: 用具体的编程语言实现 (if (stock <= 9) )
### 2. 静态与动态: 构建立体的逻辑视野
- 很多时候逻辑混乱就是因为混淆了事务的静态结构和动态行为, 一猛子扎进细节的流程里(动态), 忘了先看这一坨代码到底归属于哪个模块哪个类(静态)
- 在编程中对应两种核心视角:
    - 1. 静态结构:
        - 对象和类: 系统里有哪些角色 (用户, 订单, 状态)
        - 关系: 他们是什么关系 (用户拥有订单, 订单包含商品)
        - 数据结构: 数据是如何组织的 (是树, 是图, 还是列表)
        - 逻辑清晰的标志: 即使不运行程序, 看代码目录结构和类图就能知道这个系统长什么样子
    - 2. 动态行为:
        - 流程与交互: 数据是如何在这些静态结构之间流动的
        - 时序: 先发生什么, 后发生什么
        - 状态改变: 一个操作后, 对象的状态变成了什么
- 当乱的时候应该立刻切换视角:
    - 如果是流程乱, 画时序图或流程图
    - 如果依赖乱, 画类图或结构图
- 思维本身包括了两个层面, 思考和维度, 思考偏静态的过程, 而维度偏静态的知识组织和呈现

## 程序设计
- 模式概念:
    |模式|关系|
    |-|-|
    |继承|建立'是一个'的关系, 有限的继承可以提升开发效率|
    |组合|建立'有一个'的关系|
    |接口|建立'能做什么'的契约, 如IInteractable|
    |ECS|数据与行为分离|

    - 先从微小单元的概念开始设计一个模块

## 游戏模块设计
### 第一步：需求剖析与边界定义
这是设计的起点。在写代码之前，必须明确这个模块“是什么”和“不是什么”。
1.  **给模块下定义（高内聚）：** 用一句话概括这个系统的核心职责。
    *   *错误示例：* “背包系统用来存放道具，并在穿戴装备时加属性。”（职责越界了，加属性是属性系统的职责）。
    *   *正确示例：* “背包系统负责管理玩家拥有的物品实例（增删改查），并提供物品流转的接口。”
2.  **把自己拆成两个人（划分边界与API设计）：** 这是非常高级的系统思考方法。
    *   **“使用者（业务方）”视角：** 我根本不想知道你内部怎么实现，我只想调用 `AddItem(id, count)`，并收到一个 `OnItemAdded` 的事件。
    *   **“实现者（底层）”视角：** 我不管你要给玩家发什么奖励，我只负责校验格子够不够、生成唯一ID、写入数据库。
    *   *意义：* 这种视角切换能逼迫你设计出**高内聚、低耦合**的接口（Facade模式），防止系统间产生面条代码（Spaghetti Code）。
### 第二步：数据驱动设计
**“游戏开发，数据为王。”** 现代游戏开发通常采用数据驱动，数据结构设计往往比算法更早进行。
1.  **动静分离（极其重要）：**
    *   **静态数据（配置数据）：** 策划在Excel/JSON中填写的表。比如“屠龙刀”的ID、基础攻击力、图标路径。这部分数据在运行时是**只读**的，全服/单机只有一份内存占用。
    *   **动态数据（存档数据/运行时数据）：** 玩家具体拥有的那把“屠龙刀”的强化等级、耐久度、唯一实例UID。这部分数据需要**频繁读写、存盘、网络同步**。
    *   *意义：* 如果不动静分离，你的内存会爆炸，存档会极大，网络同步带宽高得离谱。
2.  **数据结构设计（内存布局）：**
    *   使用 Array 还是 Dictionary？需要快速按ID查找（Dict），还是需要高效遍历更新（Array）？
    *   在面向数据设计（DOD/ECS）的框架下，数据结构不仅要考虑逻辑，还要考虑 CPU Cache 命中率。
### 第三步：架构分层结构设计
一个复杂的系统必须分层，否则随着业务增加必定崩塌。游戏里常见的经典分层：
1.  **数据层（Model）：** 只维护上面第二步设计的数据，提供原子的增删改查方法。**绝对不包含表现逻辑**。
2.  **核心逻辑层（Controller/System）：** 处理业务规则。比如技能系统里的“技能前摇时间计算”、“伤害判定碰撞”。
3.  **表现层（View/Presentation）：** 播放特效、播放动画、UI刷新、播放音效。
4.  **网络层（Net/Sync）：** （如果是多人游戏）负责将玩家操作打包发给服务器，或接收服务器的下发状态进行表现。
*系统性要求：* 下层不可调用上层，平层之间尽量通过事件（EventBus）通信。**表现层可以随意抛弃和重写，但数据和逻辑层应该纹丝不动。**
### 第四步：核心算法与状态流转
在数据和架构定好之后，才去死磕具体的算法。
1.  **状态流转设计：** 游戏逻辑本质上是随时间流逝的状态机。你需要设计有限状态机（FSM）或行为树。比如一个技能的状态流转：`准备 -> 吟唱 -> 释放 -> 后摇 -> 冷却`。
2.  **具体算法：**
    *   寻路算法（A*）、碰撞检测算法、AOE伤害范围计算、洗牌算法、掉落权重随机算法等。
    *   评估时间复杂度（时间效率）和空间复杂度（内存消耗）。游戏非常看重每一帧的耗时（Tick性能）。
### 第五步：模块解耦与外部通信方案
系统不是孤立存在的，它必须和其他系统交互。怎么交互才不会死锁？
1.  **事件驱动（Event-Driven）：** 系统 A 完成某事后抛出事件，系统 B 监听。比如：成就系统监听战斗系统抛出的 `OnMonsterKilled` 事件，而不是战斗系统去调用成就系统的代码。
2.  **依赖注入与接口（Interface）：** 提炼出 `IInventory` 接口，各个模块依赖接口而不是具体的 `InventoryManager` 类。
### 第六步：非功能性需求设计
这是新手很容易忽略，但资深主程在系统设计时必须考虑的：
1.  **性能与GC控制：** 这个模块每帧 Update 会不会产生垃圾回收（GC）导致卡顿？需不需要引入对象池（Object Pool）？
2.  **网络同步与防作弊：** 谁是权威（Server Authoritative）？需要做客户端预测和回滚（Rollback）吗？
3.  **可扩展性（对于策划的宽容度）：** 如果明天策划要加一种“能吸血、同时还能给队友加护盾、死后还会爆炸”的新技能，现有的系统框架需要改代码吗？还是只需要配表？
4.  **容灾与异常处理：** 弱网断线重连后，系统的状态能正确恢复吗？
## 其他
- 细节无所谓, 流程一定要对, 流程是固定的
- 一定不要干涉别人的细节
- 分层架构底层不能牵扯上层
- 分层架构每一层都有每一层该干的事情
- Manager和Config和Factory分开
- Config必须由统一的生命周期流程拉起
- Factory用来屏蔽对象创建的复杂性, 并且在底层进行性能优化(类缓存/对象池等)
- 当设计的一个模块纯粹且泛用性强的时候就能变成一个通用组件
- 静态的总是比动态的好
- 中心访问器是搞动态扩容的, 一台机器估计跑2000, 不要一台机器常态占用一半资源, etcd可以做缓存和事务(速度比radis慢点但是支持事务)
- 最后再考虑优化
- 根据概念定流程和数据结构
